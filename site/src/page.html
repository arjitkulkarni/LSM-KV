LSM-tree key-value storage engine · C++17

A storage engineyou can crash.

LSM-KV turns random writes into one log append and one memtable insert, and compacts in the background. It was built to be killed: every acknowledged write survives SIGKILL, a torn final write and a failed fsync. The harness that proves it printed every number on this page.

Numbers

Measured,
not claimed.

A YCSB-style harness drives the engine through its public interface. Latency is measured from when a request was scheduled, not when it was sent, so stalls cannot hide. Where LevelDB wins, the table says so.

One fix, found with the engine’s own metrics.

Write throughput fell as threads were added. The commit-queue histograms showed why: a WAL append took ~3.5 µs, but writers waited ~41 µs to be woken. Queued writers now spin, then yield, then block, and the one change is reproducible with a flag.

YCSB at 8 threads.

One million 100-byte records. Ten seconds of warmup, sixty measured, three repetitions, and the median of each metric is reported.

Where the latency lives.

The full latency distribution for YCSB-A, from HDR-style histograms with at most 0.8% error per bucket. Reads resolve in memory, and the tail is updates waiting behind a flush.

What a bit of Bloom filter buys.

With the block cache disabled, every data-block fetch is a real file read. Each extra bit per key cuts the reads a missing key costs, until the filter itself stops paying for its memory.

Coordinated omission, measured.

A closed-loop client stops sending while the engine stalls, so the stall never shows up in its histogram. Open-loop mode schedules requests at a fixed rate and charges queueing to the requests that queued.

A regression, caught on the dashboard.

Shrinking the memtable from 4 MiB to 64 KiB floods L0 with tiny files. The compaction-backlog gauge climbs and writers start stalling. This is the kind of regression the metrics exist to catch.

Against LevelDB 1.23, including the losses.

Same harness, same box, same settings: 4 MiB write buffer, 10-bit Bloom filters, 8 MiB block cache, no compression. LevelDB runs through the same lsmkv::DB interface via an adapter.

Killed 200 times.
Lost nothing.

Under continuous load, the writer is killed at a random moment. On restart, every write it acknowledged has to be there, intact and at least as new as the last ack. The database directory carries over between iterations, so later crashes land in the middle of flushes and compactions.

kill

Process crash

SIGKILL mid-write. User-space buffers vanish, but the OS page cache survives, so every write acked into it must come back.

kill-sync

Group commit under fire

fsync'd writes from up to 8 threads share each fsync. Killing between the append and the ack must not produce a phantom ack.

torn-tail

Torn final write

After the kill, the newest WAL gets a partial record, garbage or zero-fill. Recovery must drop exactly that tail and truncate it.

fsync-fail

Failed fsync

The Nth fsync reports EIO. The engine must fail the write and stop acking, instead of retrying into data the kernel may have dropped.

Decisions

Choices you can
defend at a whiteboard.

A skiplist, not a red-black tree

An insert changes at most 12 forward pointers, each published with one release-store after the node is built. So readers take no lock at all, and memtable reads scale with cores.

Cost: p = 1/4 gives an expected (1/p)·log1/p n = 2 log2 n comparisons, about a balanced tree’s count, at 1.33 pointers per node.

Sharded locks, not lock-free writers

Lock-free writers invite ABA and memory-reclamation bugs, and a clean TSan run does not prove lock-freedom. Readers are already lock-free here; writers take one shard lock.

Measured: the memtable lock was never the bottleneck. The commit-queue hand-off was, and fixing it removed no lock.

Refuse to open rather than lose acks

A torn write can only be the last thing in the WAL stream. If a valid record follows the damage, the damage is corruption, and silently skipping it would drop writes that were already acknowledged.

Cost: a damaged disk needs an explicit kPointInTimeRecovery to come back up.

Limitations

What it deliberately does not do.

  • Single node. No replication or consensus.
  • No MVCC snapshots or transactions. Iterators are point-in-time.
  • Forward-only iterators.
  • No compression, range deletes or column families.
  • One background thread for flushes and compaction.
  • L0→L1 takes every L0 file: simple, but bursty.
  • SIGKILL is not a power cut. Power loss is simulated with fault injection.
  • Numbers are one laptop’s. Rerun bench/run_all.sh on yours.
